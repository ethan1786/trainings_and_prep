System Design — Mental Model + Cheat Sheet

The Flow (same for EVERY question)

1. PRODUCT REQUIREMENTS — what the user needs
2. FACTS — inbound data, outbound users, volume, scale
3. FACTS → CONSTRAINTS → DECISIONS — each fact forces a design choice
4. TRACE THE DATA PATH — draw real components as you explain
5. FAILURE MODES — walk back through, what breaks at each step

The Hard Problem — Say in First 2 Minutes

ExploreFanout — pushing right deltas to 2M users. Ingestion is solved; delivery is not.
Exchange OrderUser wants instant certainty, exchange is slow/unreliable/might silently fill or drop. Bridge that gap without losing money.
Credit ApprovalUser wants instant answer, evidence comes from slow flaky providers. Need bounded deadline that stays honest.
Object StorageDeletion — every chunk might be shared. Delete too eagerly = data loss. Too conservatively = storage leak.

Universal Financial System Principles

1. Atomic hold before acknowledging (prevent double-spend)
2. Kafka for async decoupling + replay + audit trail
3. Idempotency at every boundary (client→you, you→provider)
4. Reconciliation as permanent safety net (not error handling)
5. Provider is the authority (never assume state, always verify)
6. State machine with explicit terminal states
7. Consistency > availability for money movement
"I need: atomic holds to prevent double-spend, idempotency to prevent double-execution, reconciliation to catch lost callbacks, and clear authority on who decides state in a race."

Order System — Data Path

User → API Server (validate + hold funds + persist order) → return 200
→ Order Engine (one service: find best price → submit to exchange with idempotency key)
→ External Exchange (async — may take seconds)
→ Webhook callback: filled/partially filled/rejected
→ Update DB + adjust hold + update position → Notify user
Safety net: Reconciliation Poller → query exchange for stuck orders → resolve

Order System — Failure Recovery

Exchange timeoutPoller detects stuck > 60s → queries exchange → filled? apply. Not filled? cancel + retry next exchange.
Webhook never arrivesSame as timeout — poller catches it
Double submitIdempotency key (order_id) on exchange. Exchange returns existing order.
User cancels mid-fillExchange is authority. Query state first. If filled → fill wins. If open → cancel.
Concurrent orders (same account)Atomic hold in DB transaction (SERIALIZABLE). Second order sees reduced balance.
Traffic spike (1000x)Kafka queue absorbs burst. Workers process at controlled rate. 429 if queue full.

Credit Approval — Data Path

User → POST /apply → 200 (application_id) → client polls every 500ms
→ Processing server: fan out to providers in parallel (identity, bureau, fraud, income)
→ Each provider: sync response OR async callback
→ As each responds: update DB status → client sees progress on next poll
→ All mandatory checks done within deadline? → auto-decide (approve/deny)
→ Deadline hit with incomplete evidence? → manual_review (honest fallback)
→ Decision snapshot: freeze policy_version + signals + reason codes (immutable)

Credit Approval — Failure Recovery

Provider timeoutPer-provider timeout (3s). One retry if time remains in budget. If still fails → route to manual_review.
Provider down (circuit open)Circuit breaker trips. Skip that check. Route to manual_review with reason "provider unavailable."
Conflicting signalsPolicy routes to manual_review. Preserve both observations in history.
Deadline expiresReturn manual_review honestly. Never hang the response. Never guess.
Duplicate applicationIdempotency key (session_id). Return existing application_id.
Crash mid-processingEach provider result persisted independently. On restart, check what's done, resume from there.

Object Storage — Data Path

Upload: Client → API Gateway (chunk file into 64MB pieces, compute SHA-256 per chunk)
→ Check metadata: chunk hash exists? Skip (dedup). New? → issue presigned URL
→ Client uploads directly to data nodes (gateway never proxies bytes)
→ Replicate chunk to 3 nodes (rack-aware) → commit manifest atomically (Postgres)
Download: Client → Gateway → lookup manifest → presigned URLs → client fetches from data nodes
Delete: Remove object row + decrement ref counts → zero? → GC queue (24h grace)

Object Storage — Failure Recovery

Upload interruptedManifest never committed → object not visible. Orphan chunks cleaned by GC later.
Data node diesHeartbeat timeout (30s) → identify under-replicated chunks → re-replicate from surviving copy to new node.
GC races with upload24h grace period. Don't delete zero-ref chunks immediately. Upload commits within hours → count goes back above 0.
Ref count driftPUT/DELETE wrap ref-count update in same transaction as object row. Can't drift.
Bit rotBackground scrubber re-computes SHA-256 per chunk. Mismatch → corrupt → re-replicate from healthy copy.
Read during node outage3 replicas. Client falls back to another replica. Transparent.

DON'T FORGET

Coalescing: "Can I push everything to 2M users?" NO → batch per 250ms
Stale: heartbeat missing → mark flag → propagate to UI
Hold BEFORE 200: validate + hold + persist in one atomic txn
Query before retry: never blindly re-submit to exchange
